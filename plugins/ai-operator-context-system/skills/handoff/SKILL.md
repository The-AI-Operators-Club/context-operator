# Handoff

Package only the state a receiver needs to continue a **specific assignment**. Handoff selects from current Project Context and a Task Specification when available; it does not reconstruct the whole project's durable state (Compress) or perform the receiving task. Follow the [shared doctrine](references/context-doctrine.md), [information states](references/information-states.md), [terminology](references/terminology.md), [Project Context schema](references/project-context.md), and [Task Specification schema](references/task-specification.md). The [handoff template](assets/handoff-template.md) is a selective output aid, not a form to fill mechanically.

## When to use

Use for an explicit handoff or when the user wants another agent, new session, model, or collaborator to continue a known piece of work. A request to continue in a new chat can imply transfer intent. Do not activate for a generic project summary, history compression, documentation, or a request to recommend next steps without a receiver or continuation intent.

## Workflow

1. Identify the receiver and its immediate assignment from the request and available task material. Keep the broader Objective distinct from what the receiver must do now. If the assignment cannot be determined, ask exactly for the work to continue (for example, “What immediate assignment should the next agent continue?”). A generic receiving agent is sufficient if identity is unknown; do not ask who the receiver is just to make the handoff. Do not invent an assignment. Use available context before asking.
2. Read existing Project Context and Task Specification when available. Select only facts, current state, decisions, constraints, files/resources, completed work, known problems, and open questions that change this receiver's work. Preserve exact callable/interface contracts needed by the assignment (including argument shape) when the receiver will not have the upstream source; a function name alone may be insufficient. Adapt detail to the receiver's role and access; do not name an upstream artifact as a receiver resource when the transfer explicitly excludes it. A decision such as a timestamp convention can be omitted when the receiver's assignment does not touch timestamps. Do not transfer unrelated history, secrets, or whole source documents by default.
3. Preserve information status and authority. Keep Decisions separate from Constraints; an authorized numerical cap stays a Constraint, not a Decision, and should appear once. A hypothesis, assumption, preference, or proposal is not a settled choice. Exclude obsolete state as current. Mention a superseded choice briefly only when it prevents confusion. Put an item under **Do Not Reopen** only when it is an explicitly settled choice, relevant to this assignment, and reopening would waste effort. Completed work belongs under Completed Work; unrelated history is omitted entirely. Never put a tentative idea, task deferral, or unresolved question under Do Not Reopen; an open policy can remain out of scope for this assignment without becoming settled.
4. Produce a portable handoff with only useful sections from the template. Include enough completed work to prevent repetition, not a chronological account. Preserve unresolved questions and the impact of uncertainty. State each item once: put completed implementation under Completed Work rather than repeating it in Current State; put unresolved policy under Open Questions rather than also under Constraints; put a hard boundary, including a numerical cap the receiver must enforce, under Constraints rather than Requirements; put a decision under Decisions rather than restating it as a constraint. Requirements may refer to a constraint when needed to explain the implementation step, but do not leave the constraint only in Requirements. Include a **Next Action** only when source or task explicitly establishes one; the Immediate Assignment already tells the receiver its job. Do not infer strategy, priority, or missing project state.
5. Audit from the receiver's point of view: can it act correctly without reopening settled choices or repeating completed work, while recognizing open questions? Check every referenced callable against the source context or available file and transfer any missing argument contract. Compare sections line by line and remove repeated propositions; for example, if Completed Work says the cancellation service method and tests are done, Current State need only say the endpoint is missing. If Open Questions says email policy is unresolved, do not repeat that under Constraints. Delete unrelated details entirely, including lists that announce they are out of scope. State a task exclusion only if it prevents a plausible mistake in this assignment. A reply alone does not save or synchronize the handoff; write a file only when requested or needed by the current workflow. Stop at the handoff unless the user also requested execution.
